# AI-Powered-Journal

A single-user-per-account journal that saves your writing **before** it talks to a model,
then reflects on it.

## What actually works today

**Write an entry, get a reflection.** You write; the entry is written to SQLite and
committed *first*; only then is Groq called to produce a mood label, a 1–10 mood score, and
a short reflection. If the analysis fails for any reason, **the entry is already on disk** and
you get a plain sentence instead of a stack trace.

**Accounts.** Signup (closed by default), login, logout, session handling, CSRF protection,
and per-user data isolation — every entry query is scoped by `user_id`, and there is a test
that fails the build if that ever stops being true.

## What is planned and NOT built

Listed here so the gap is visible rather than discovered:

- **Charts, trends, and any visualisation.** There is no dashboard.
- **A JavaScript frontend.** The UI is server-rendered Jinja templates with no JavaScript.
- **Encryption.** The database is a plain SQLite file. It is not encrypted at rest.
- **Machine learning.** Nothing is trained. Mood analysis is a single call to a hosted LLM
  with a written prompt.
- **Editing entries.** You can write and read. You cannot edit or delete.
- **Password reset, email verification, rate limiting.**
- **A background worker.** Analysis is synchronous — the request waits on Groq.

## Running it

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements-dev.txt

# .env is gitignored and must contain:
#   SECRET_KEY=<python -c "import secrets; print(secrets.token_hex(32))">
#   GROQ_API_KEY=<your key>
# Missing SECRET_KEY is fatal. Missing GROQ_API_KEY only disables analysis.

flask create-user you@example.com    # signup is closed by default
flask run
```

Tests:

```bash
python -m pytest tests/ -q
```

Production is `gunicorn "app:create_app()"` — the app factory, so every launch path gets the
same configuration.

## Layout

| File | Responsibility |
|---|---|
| `app.py` | The app factory. Every launch path calls `create_app()`. |
| `config.py` | The only place `os.environ` is read. |
| `db.py` | Connection handling and `PRAGMA user_version` migrations. |
| `auth.py` | Accounts, sessions, CSRF. |
| `journal.py` | Journal routes. Every query is scoped to the logged-in user. |
| `analysis.py` | The only module that talks to Groq. |
| `templates/` | Jinja. `base.html` carries the site-wide safety line. |

## Design decisions worth knowing

**Save first, analyse second.** The write is committed before the network is touched.
Everything between the two can fail — network, DNS, timeout, bad key, rate limit, malformed
JSON, the process being killed. Save-first means the writing survives all of it. The cost is
one extra local SQLite write.

**A pending row is the retry queue.** A failed analysis leaves `analysis_status='pending'`,
findable and recoverable. Fix the cause, sweep, everything catches up. This only works
because the entry was saved first and because "unknown" is stored as `NULL` rather than `''`
— which is why those two decisions are load-bearing rather than stylistic.

**`SECRET_KEY` is fatal, `GROQ_API_KEY` is a warning.** Match the response to the scope of
the failure. A missing secret key means nobody can log in — the app is entirely not working.
A missing Groq key costs one feature, and refusing to boot would turn a degraded feature into
a total outage *and* lose every entry written while the key was wrong.

**Analysis is a reflection, not advice.** The prompt forbids advice, diagnosis, and
action-suggesting questions — though models do not always obey. The crisis line at the bottom
of every page is **static HTML, generated by no model**, precisely so it cannot fail.

## A note on the model

The same entry text produces different mood labels across runs. This is not a bug and it is
not fixable by prompting harder. Labels are drawn from a closed 11-word vocabulary to bound
the variance, but bounded is not eliminated. The app never assumes a stable label for a given
text.
